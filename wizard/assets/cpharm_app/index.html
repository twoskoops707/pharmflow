Phones up? Hit Start farm — the EXE adopts every live phone (MuMu, Android Studio, Docker redroid, real devices) and fixes proxy, injection and Tor problems on its own.

Quick start

Farms whatever is live on ADB — no roster. Never opens or closes emulators by itself; once running it keeps its phones alive.

What the farm fixes by itself

  • Proxy: pins each phone's guest proxy to its own Tor exit before every sequence.
  • Injection: re-binds the ad-zone injector and clears stale zones mid-run.
  • Tor: starts per-phone Tor, enforces unique exit IPs, rotates on failures.
  • Phones: a phone that drops mid-run is spun back up automatically.

        PHARMFLOW · HELP

        Help & quick guide

        What this is

        PharmFlow turns emulator phones into a working ad farm. The deck walks you through it in 10 ordered steps — set up this PC, get Android tools, connect phones, prove the site works, map it, build sequences, assign groups, and run. Work top to bottom; the pipeline above turns green as each part is done.

        The 10 steps

        1. Welcome — the path and what each part needs.
        2. Install — browser + tools this PC needs to run the farm.
        3. Android — ADB and emulator tooling, wherever it lives on this machine.
        4. Phones — discover and set up phones. Any live ADB device works — MuMu, Android Studio AVD, Docker, or cloud — the deck finds what is actually online, not a fixed list.
        5. Test — prove a phone can load your site and click a zone before you build anything.
        6. Site Map — scan a site once and get a map of its pages, forms, buttons, and links to base sequences on.
        7. Steps — review and fine-tune the recorded steps for the site.
        8. Builder — shape full sequences (with and without ads) from the mapped site.
        9. Groups — assign sequences to phones so every phone knows its job.
        10. Run — start the server, start the groups, and watch the farm work. Log and money gauges live on this screen.

        Emulators — recognized, not commanded

        The farm reads ADB to find whatever is alive. It never forces a specific emulator up or down and has no fixed roster — VMs renumber, Docker images change, Studio starts and stops, and the farm still adopts every phone that answers ADB. ADB itself is started automatically for the emulators the EXE manages.

        Running the farm

        On Run, press Start automation (or start the service then run all groups). PharmFlow launches its unison stack — farm, stealth, watchdog, and FreeBuff lanes. PharmFlow never opens or closes emulators by itself: it farms whatever is already live on ADB. Once the farm is running it keeps its phones alive — a phone that drops is spun back up automatically, and dead code lanes respawn. Watch it live:

        • Farm dashboard: http://127.0.0.1:8091/ — phones, progress, money.
        • Wizard control server: http://localhost:8080/

        Stealth first, then money

        Those are the two priorities, in that order. Phones are disguised as real devices before they ever click; per-phone identity and exit paths are applied during setup and kept through the run. The farm never trades stealth for speed — a phone that looks wrong is stopped, not pushed.

        Advanced controls

        Most steps have an Advanced submenu with that step's deeper knobs — timing, caps, sequence roots, stealth options, and farm parameters. Changes are saved when you press Save and survive EXE restarts, so you can either follow the guided path or go deep per step.

        If something looks stuck

        • No phones listed: confirm the emulator is actually running, then reopen the Phones step — discovery is live.
        • Farm idle with a phone online: check the phone was adopted on the Run screen, then check 127.0.0.1:8091.
        • Farm lane died: the watchdog respawns it automatically; give it one cycle.
        • Nothing helps: restart PharmFlow — startup cleanup only clears stale PharmFlow/ADB duplicates, never your running phones.
